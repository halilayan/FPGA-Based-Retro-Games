# Basys 3 Retro Game Console — v1

## Platform

- **Board**: Digilent **Basys 3** — Xilinx/AMD **Artix-7** FPGA, part
  number **`xc7a35tcpg236-1`** (xc7a35t, cpg236 package, speed grade -1).
- **Tools**: Xilinx/AMD **Vivado 2022.2** (hardware) + **Vitis 2022.2**
  (software) — not tested with any other version.
- **Architecture**: VHDL RTL + embedded **MicroBlaze** CPU (soft core),
  320x240 pixel VGA output, keyboard input (PS/2 or UART relay).

**v1**: 6 games (Pong, Snake, Breakout, Tetris, Frogger, Flappy Bird),
real RGB444 colors (via `console_gpu_axi.vhd`'s CPU-writable 256-color
palette), running over JTAG without using flash.

## Folder structure

```
hdl/
  video/      Framebuffer, VGA timing, palette RAM, font ROM — the video
              pipeline
  gpu/        console_gpu_axi.vhd (the CPU-facing GPU/palette/blitter/
              collision register interface), asset ROM, BRAM adapters,
              arbiter
  input/      PS/2 + UART keyboard pipeline (debounce, scancode FIFO,
              PS/2 receiver, AXI-facing register interface)
  common/     Small shared blocks (clock generator, 2-FF synchronizer,
              blink)
  cart/       An earlier "cartridge" abstraction plus a standalone
              pure-VHDL Pong demo (hdl/cart/games/) kept for reference —
              NOT used by the current MicroBlaze+C system
  tops/       Standalone bring-up/test top-levels from early development
              phases (video-only test, -only test, pure-VHDL
              Pong) — NOT the design actually running on the board; the
              real top-level is auto-generated by Vivado as an HDL
              wrapper around the Block Design (see the hardware setup
              steps below)

tb/           One testbench per hdl/ module, plus shared bus-functional
              models in tb/bfm/ (AXI-Lite and PS/2 drivers)
constraints/  Basys3 pin constraints (.xdc) — standard pinout, no edits
              needed for a normal build
bd/           Block Design Tcl export (system_bd.tcl) — recreates the
              full wired-together system (MicroBlaze, GPU, ,
              clocking, memory controllers...) in one step

sw/
  kernel/     Shared, game-independent code: boot screen, menu, pause
              overlay, main loop, and the game roster (gamelist.c)
  libconsole/ The hardware-abstraction API every game is written
              against (gfx.*, pal.*, kbd.*, joystick.*, sys.*), plus
              port/hw.c (real board backend) and port/host.c (PC-side
              simulation backend for testing without hardware)
  games/      One game = one .c/.h pair (e.g. snake.c / snake.h), written
              only against the libconsole/ API above. To add a new game:
              copy the structure of any existing game file as a
              template, then register it in sw/kernel/gamelist.c

tools/        Python tools: makefont.py (font asset generation),
              kbd_relay.py ( relay over UART)
```

## Setting up the hardware — step by step

`bd/system_bd.tcl` is a COMPLETE, up-to-date export of this project's
Block Design exactly as it is CURRENTLY running and tested on real
hardware — including the `console_gpu_axi_0`↔`video_out_0` palette
wiring — with all configs ready. Following the steps below and running
this file recreates the system we currently have set up, from scratch,
on YOUR OWN computer, identically:

1. Open Vivado and create a **new project**: select
   **`xc7a35tcpg236-1`** as the target device (it can also be found by
   searching "Basys3" in the Boards list, but use the exact part number
   for a precise match).
   - (You can also skip this step — running `system_bd.tcl` without an
     existing project automatically creates one for you with the
     correct part number. However, creating the project manually makes
     it easier to add files through the GUI in steps 2-3.)
2. In the Sources tab, use **Add Sources** → add ALL `.vhd` files under
   `hdl/` (including subfolders) as design sources.
3. Again use **Add Sources** → add `constraints/basys3.xdc` as a
   constraints file.
4. Open the Tcl console (Window → Tcl Console) and run:
   ```tcl
   source bd/system_bd.tcl
   ```
   This fully builds the Block Design named `system_bd` (MicroBlaze,
   clock generator, UART, framebuffer/asset BRAM controllers, GPU/
   palette/blitter/collision AXI interface,  GPIO, XADC
   joystick — all with the correct connections), then validates and
   saves it.
5. In the Sources tab, right-click the Block Design (`system_bd.bd`) →
   **Create HDL Wrapper** (let Vivado auto-update it).
6. Click **Generate Bitstream** in the left panel (this automatically
   runs synthesis + implementation first).
7. Once the bitstream finishes: use **File → Export → Export Hardware**
   to export the `.xsa` file (the file Vitis will use as its hardware
   platform — make sure to check "Include bitstream").

> **If you later modify the BD through the GUI**: keep `bd/system_bd.tcl`
> up to date by right-clicking the Block Design tab → **Export Block
> Design**, overwriting this file with the refreshed export.

## Setting up the software

1. Using the `.xsa` generated above, create a new platform project
   (standalone domain, MicroBlaze).
2. Create a new application project, and copy the `.c`/`.h` files from
   under `sw/kernel/`, `sw/libconsole/` (including `port/hw.c`, but
   **not** `port/host.c`) and `sw/games/` into a single flat `src/`
   folder (these files were written assuming "flat include", so you
   don't need to preserve the subfolder structure). `port/host.c` is a
   PC-side stand-in for the same functions `port/hw.c` implements for
   the real board (`pal_set_color`, `gfx_clear`, ...) — copying both
   into the same project causes duplicate-symbol link errors.
3. Build and program the board.

After step 2, your Vitis project's `src/` folder should look like this
(35 files, all flat, no subfolders):

```
src/
  breakout.c   breakout.h
  demo.c       demo.h
  flappy.c     flappy.h
  font8x8.h
  frogger.c    frogger.h
  gamelist.c   gamelist.h
  gfx.c        gfx.h
  hw.c                        <- from sw/libconsole/port/hw.c
  joystick.c   joystick.h
  kbd.c        kbd.h
  kernel.c     kernel.h
  main.c
  menu.c       menu.h
  pal.c        pal.h
  pause.c      pause.h
  pong.c       pong.h
  snake.c      snake.h
  sys.c        sys.h
  tetris.c     tetris.h
```

### Adding your own game

Every game is just one `.c`/`.h` pair written only against the
`libconsole/` API: `gfx.h` (drawing), `pal.h` (colors), `kbd.h` /
`joystick.h` (input), `sys.h` (timing/vblank). To add a new one:

1. Copy an existing game (e.g. `snake.c`/`snake.h`) as a template, and
   look at how it structures its init/step/draw functions and its own
   `pal_set_color()` palette setup.
2. Write your `yourgame.c`/`yourgame.h` the same way and drop both
   files into `src/` alongside the others.
3. Register it in `gamelist.c` (add it to the game roster the menu
   reads from, and `#include` its header there).
4. Rebuild — your game now shows up in the menu.

## Game controls

| Game | Controls |
|---|---|
| Pong | Up / Down — move paddle |
| Snake | Arrow keys — change direction |
| Breakout | Left / Right — move paddle |
| Tetris | Left / Right — move, Up — rotate, Down — soft drop, Enter — hard drop |
| Frogger | Arrow keys — hop |
| Flappy Bird | Z — flap |

Everywhere else: **Esc** opens the pause menu during a game (Up/Down to
pick Resume/Restart/Quit, Enter to confirm), and **Enter** confirms/
selects on the boot screen, main menu, and score screen.

## Keyboard on real hardware

A wireless keyboard does not work with the Basys3's USB HID host (hub/
composite devices aren't supported) — so the keyboard is instead
relayed from the PC over UART. AFTER the board has been programmed, on
the PC run:

```bash
pip install pyserial keyboard
sudo python3 tools/kbd_relay.py --port /dev/ttyUSB1
```

(`sudo` is required — the `keyboard` library reads raw input devices on
Linux. The port name may vary between machines; check with
`ls /dev/ttyUSB*`.)

## Resource utilization (Vivado 2022.2, xc7a35tcpg236-1, Routed)

| Resource | Used | Utilization |
|---|---:|---:|
| Slice LUT | 2108 | 10.18% |
| Slice Register (FF) | 1990 | 4.68% |
| BRAM | 44.5 / 50 blocks | 89.00% |
| DSP | 7 / 90 | 7.78% |

BRAM usage is above the 85% target — this budget should be checked
before adding anything that needs new memory (e.g. a tile engine).

## Known limitations (v1)

- LMB (64 KiB) usage is very high (real color palette code + 6 games) —
  Pong 2P (nearly identical to Pong) was removed for this reason; memory
  needs to be freed up / code paging introduced before adding new games.
- The CPU cannot read back the framebuffer — on some screens (e.g. the
  pause overlay) restoring the background may not work fully.
